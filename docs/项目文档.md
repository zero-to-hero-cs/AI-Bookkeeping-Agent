## 一、方案设计

### 1.1 整体架构

```
   用户
    │  一句话（"打车32" / "上个月交通花了多少"）
    ▼
┌──────────────┐  写 input.txt    ┌──────────────┐  写 data.txt / query.txt  ┌──────────┐
│    ui.py     │ ───────────────► │   main.py    │ ─────────────────────────► │ calc.exe │
│  终端交互层   │                  │  AI 意图识别  │                            │ C 计算层  │
└──────────────┘                  └──────────────┘                            └──────────┘
    ▲                                     │                                        │
    │          读 reply.txt               │  大模型 API（可选）                      │ 读 budget.txt
    └─────────────────────────────────────┘                                        │
    ▲                                                                              │
    │                            读 result.txt                                     │
    └──────────────────────────────────────────────────────────────────────────────┘
```

四层职责：

| 层 | 文件 | 只做三件事 |
|---|---|---|
| 界面层 | `ui.py` | 接收用户输入、调用下层、把结果打印出来 |
| 智能层 | `main.py` | 意图识别（记账 / 查账 / 追问 / 拒绝）、写入数据文件 |
| 计算层 | `calc.c` | 读账本和查询条件，算分类小计与超支判定 |
| 支撑层 | `fileio` 逻辑 + `tools/` | 文件协议、自检 |

### 1.2 为什么用「文件」当接口

- **可并行**：五个人水平不一，靠文件协议可以各自独立开发、拿假数据自测，互不阻塞。
- **可观察**：出问题时打开 4 个 txt 就能定位是哪一环错了，不需要加断点调试。
- **跨语言**：C 和 Python 通过文本通信，不依赖任何 FFI 绑定。
- **可降级**：任何一层缺失（比如 `calc.exe` 没编译）都能给出明确提示而不是整体崩溃。

代价我们也清楚：多了一次磁盘 IO、没有事务、并发需要加锁。当前数据量（月均几十条）下这些代价可以接受。

### 1.3 数据文件协议（冻结版）

| 文件 | 谁写 → 谁读 | 格式 |
|---|---|---|
| `data/input.txt` | UI → main | 一行用户原话 |
| `data/data.txt` | main → calc | `日期,类别,金额`，如 `2026-11-27,交通,32.00` |
| `data/query.txt` | main → calc | 三行：类别（或 `ALL`）/ 开始日期 / 结束日期 |
| `data/budget.txt` | UI → calc | 一个数字 |
| `data/result.txt` | calc → UI | `总计:702.11, 交通:50.00, …, [WARNING]` |
| `data/reply.txt` | main → UI | 第 1 行 `TYPE=ok/ask/query/refuse/error`，第 2 行起正文 |

**单写者原则**：每个文件在同一时刻只有一个写入者，从结构上避免写冲突。

### 1.4 意图识别流程

```
输入 → 是否越界/收入类？ → 拒绝
     → 是否多笔消费？     → 拆成多条记录
     → 是否查账（含查询词且数字无货币单位）？ → 写 query.txt
     → 有金额缺类别？     → 追问，状态存 pending.json（10 分钟过期）
     → 金额类别齐全？     → 追加账本
```

### 1.5 关键设计决策

| 决策 | 原因 |
|---|---|
| **不让模型算日期** | 模型只输出原话里的时间词（"上个月"），日期换算由 Python 的 `datetime` 完成。模型算日期错误率高，且这类错误现场最难解释 |
| **`temperature = 0`** | 这是结构化抽取不是创作，必须保证同一输入稳定输出 |
| **入库前强校验** | 金额必须 `0 < x ≤ 1000 万` 且为有限数；类别不在枚举内落「其他」。宁可追问，不写脏数据 |
| **断网自动降级** | 无 Key / 超时 / 限流 / 返回非法 JSON → 退回本地关键词规则，保证演示不中断 |
| **C 只做计算** | C 模块不碰模型、不碰界面，输入输出边界清晰，便于单测（`tools/check_calc.py` 用 Python 独立算一遍对答案）|
| **不用 SQLite** | C 读数据库需链接 sqlite3 库，会显著增加构建复杂度。账本采用 **CSV 结构化存储**（固定三字段），已满足"结构化、可查询"；数据量上万时应换成 SQLite + 导出快照的混合方案 |

## 二、遇到的问题与解决方式

### 2.1 AI 相关

| 问题 | 现象 | 解决 |
|---|---|---|
| 模型输出带 markdown 代码块 | 返回 ` ```json {...} ``` `，`json.loads` 直接失败 | 加 `_extract_json()`：剥掉围栏、截取首尾大括号 |
| 模型返回格式不受控 | 偶尔给出 `amount: "32元"`、负数、超大数 | 入库前统一走 `normalize_amount()`，非法值转成追问 |
| 模型被要求算日期 | 算"上个月"经常差一天 | 模型只输出时间词，日期由本地换算 |
| API Key 含全角字符 | `requests` 抛 `'latin-1' codec can't encode` 这种看不懂的错 | 启动时检查 ASCII，不是就提示并降级 |
| 断网 / 欠费 | 整个程序不可用 | 本地规则兜底 + 失败重试 1 次 |

### 2.2 解析正确性

| 问题 | 现象 | 解决 |
|---|---|---|
| 查账句里的数字被当金额 | 「最近7天花了多少」→ 追问"7.00 元这笔记哪类" | 有查询词且句中数字**没有货币单位**时，不当金额 |
| 追问污染后续指令 | 追问后输入「买衣服」，被记成上一轮的金额 | 只有"短句/纯数字/分类词"才当作对追问的回答，否则丢弃 pending |
| 一句话多笔只记一笔 | 「午饭28，打车32」→ 只记 28 或类别金额错位 | 按标点切句逐段解析，多笔分别入库并逐笔显示 |
| 多笔共用一个日期 | 「昨天打车32，今天午饭28」两笔都是今天 | 逐段识别日期，没写日期的沿用前一段 |
| 中文数字认不出 | 「十块钱」反复追问，无法记账 | 加中文数字解析（十块/二十五/一百二/十块五/五毛） |
| 数量词被当金额 | 「买了三个苹果」被记成 3 元 | 中文金额只认带"十/百/千/万"的词 |
| 取消词太死 | 「算了，不记了」取消失败 | 取消判定改为模糊匹配并去除标点 |
| 负数被吞掉符号 | 「-5」记成 5 元 | 出现负号直接拒绝（本项目不支持退款） |
| 科学计数法截断 | 「1e999」被截出 999 元 | 识别到 `1e9` 形式直接拒绝 |
| 收入被记成支出 | 「工资到账8000」记成一笔支出 | 识别收入/退款类词，明确回复"暂不支持记账收入" |
| 未来日期 | 「12月1日交房租」记成未来，当月查不到 | 已知限制，保留原语义（用户确实可能预记） |

### 2.3 跨语言与文件

| 问题 | 现象 | 解决 |
|---|---|---|
| 账本格式变更 | C 按两列解析，三列时把日期当类别、金额算成 0 | 按第二个逗号切分，同时兼容两列/三列 |
| C 不读查询条件 | 查"交通"返回全账本总和 | 增加读 `query.txt` 并按 `strcmp` 做日期区间过滤 |
| 百分比精度丢失 | `%.0f` 让 0.01 变成 0 | 统一 `%.2f` |
| 中文在 result.txt 乱码 | 源码编码与输出编码不一致时"总计"变乱码，界面永远显示 0 元且不报错 | 协议关键字用 UTF-8 字节转义写入 |
| 文件带 BOM | 记事本保存后，C 读第一行整行丢弃、总计变 0 | C 侧读取时跳过 `EF BB BF`；Python 侧统一 `utf-8-sig` |

### 2.4 界面与工程

| 问题 | 现象 | 解决 |
|---|---|---|
| `os.system("calc.exe")` | 弹出 Windows 自带计算器 | 改 `subprocess.run([绝对路径], cwd=项目根目录)` |
| 调用失败无提示 | 界面只显示"未收到回复" | 捕获返回码与 stderr，原样转给用户 |
| 调 main 前不删旧回复 | main 崩溃时显示上一次的结果（假成功） | 先删 `reply.txt`，再判断是否生成 |
| 查账沿用上次条件 | 显示"总支出 50 元"但下面列着 702 元分类 | 空回车时重新写入"本月总账"查询条件 |
| 查无记录却列出全部分类 | 标题写"娱乐"，内容却是餐饮和购物 | 查特定分类无记录时直接提示，不回退显示全部 |
| 预算跨期比较 | 查"上个月"也报"本月超支" | 仅在查询区间为本月时做预算比较 |
| 并发写 | 两个实例交叉读写 | `data/.lock` 文件锁，抢不到锁就写错误提示，不动账本 |
| 无顶层兜底 | 任何意外直接抛栈，UI 无响应 | `run()` 外层 `except`，统一写 `TYPE=error` |
| Windows 中文乱码 | GBK 终端打印报错 | 统一 `sys.stdout.reconfigure(encoding="utf-8")` |
| bat 路径含空格 | 用户名带空格时启动失败 | `"%PY%"` 加引号 |

## 三、未完成的部分及原因

| 未完成项 | 原因 | 替代方案 |
|---|---|---|
| **小票/截图 OCR 录入** | 需要付费视觉 API；拍照识别率不稳定（光照、褶皱、小票字体）；只对应 MVP 第 1 项的一个子项 | 用「一句话记账」覆盖同一场景，识别率和稳定性更高 |
| **SQLite 数据库** | C 模块读数据库需链接 sqlite3，构建复杂度显著上升，且破坏"文本协议 + 跨语言"的架构 | 使用 **CSV 结构化存储**（固定三字段），已支持按时间区间与分类聚合查询；数据量上万时按 1.5 节的方案演进 |
| **在线可访问 Demo** | 时间优先用于保证本地可复现性（评审可在自己环境跑通） | 提供 Docker 一键构建 |
| **月度趋势图** | 饼图已覆盖"分类占比"这一可视化要求，趋势图属于可选加分项 | 保留 `--chart` 的分类饼图 |
| **图形界面** | 容器内无显示器，tkinter 无法启动 | 终端菜单界面在 Windows 与容器内表现一致，更利于复现 |
| **多人账号提交记录** | 队友的 GitHub 协作者邀请未及时接受 | 分工在 README「团队分工」中说明，答辩时说明负责模块 |

## 四、可复现性说明

| 步骤 | 命令 | 说明 |
|---|---|---|
| 装依赖 | `pip install -r requirements.txt` | requests 必需；matplotlib 仅饼图需要 |
| 编译 C | `gcc calc.c -o calc.exe -Wall -O2` | Windows 无 gcc 时可用 VS：`cl /utf-8 /O2 calc.c` |
| 灌演示数据 | `copy examples\示例账本.txt data\data.txt` | 让评审无需自行构造数据 |
| 运行 | 双击 `run.bat` 或 `python ui.py` | 推荐 bat：自动切目录、设 UTF-8、查找 Python |
| 自检 | `python tools\check_calc.py`（需 calc.exe）<br>`python tools\test_llm.py`（不需要 Key） | 前者 6 个场景对答案，后者 14 项断言 |
| Docker | `docker build -t jizhang .`<br>`docker run -it --rm -v "%cd%/data:/app/data" jizhang` | 镜像构建时自动编译 `calc.exe`；`/app/data` 已声明为数据卷，账本持久化在宿主机 |

## 五、已知限制

1. **单机单用户**：文件协议面向个人使用，不支持多端并发写（有文件锁兜底）。
2. **金额用 double**：金融场景应使用定点数或整数分；本项目金额范围小，可用 `%.2f` 输出。
3. **本地规则覆盖率有限**：离线模式下靠关键词表，遇到复杂表述（"和同事 AA 后我付了 120"）识别率低于大模型。
4. **未来日期**：预记未来支出后，当月查询看不到，属设计取舍。
5. **OCR 未实现**：见第三节。
